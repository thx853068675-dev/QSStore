# VPN 下载复核

## 问题与修复

旧任务始终将镜像作为首选，即使设备已开启 VPN。系统下载代理的自动重试还会延长无数据连接的等待；只要缓慢收到数据，旧逻辑便一直等待该线路。

- 新任务在 600ms 内检查活动 VPN，开启时优先 GitHub 官方地址，保留镜像备用。网络权限或服务不可用时沿用原顺序。
- 有备用线路的新下载，12 秒无数据或 15 秒首段速度过低时换源。首段门槛最多 512 KiB；已完成四分之一的小包、已有系统断点及最后一条线路不会因慢速被放弃。
- 已存在的系统任务按原 URL 接管，不为重排线路丢弃断点。进程挂起后继续读取代理实际进度；不设整包总耗时限制。
- 显式允许计费网络，避免系统代理默认 `metered=false` 导致下载等待。
- 网络权限使用 SDK 的 `GET_NETWORK_INFO`，不弹额外用户授权框。

## 7.0 实测

使用同一个已发布的 51 预览 HAP（13,833,574 字节）。测试页调用生产 `AssetDownload` 与系统后台代理，但不写入实际安装队列，也不签装其他应用。

| 条件 | 方式 | 结果 |
| --- | --- | --- |
| VPN 关闭 | gh-proxy 系统后台下载完整包 | 52,853ms，约 256 KiB/s |
| VPN 开启 | 普通 HTTP 流，gh-proxy | 30,028ms 收到 358,081 字节，约 11 KiB/s，测试主动停止 |
| VPN 开启 | 普通 HTTP 流，GitHub 直连 | 30,804ms 收到 344,055 字节，约 10 KiB/s，测试主动停止 |
| VPN 开启 | 普通 HTTP 流，ghfast | 30,015ms 收到 261,227 字节，约 8 KiB/s，测试主动停止 |
| VPN 开启 | ghfast 系统后台代理 | 39,478ms 收到 352,256 字节，测试主动停止 |
| 随后关闭 VPN | 同一 gh-proxy HTTP 请求首 1 MiB | HTTP 206，4,323ms，约 236 KiB/s |

生产下载器的 VPN 识别与零字节换源已在设备记录中确认：GitHub 直连开始后约 12 秒转到 gh-proxy。最终 512 KiB 首段门槛另有回归测试覆盖实际观察到的 16 KiB/s 慢速场景。

结论：安装器的固定镜像顺序存在问题，已修复；当前设备的 VPN 路径也明显拖慢两种下载接口和三个源。此测试不能证明具体是节点带宽、代理规则还是隧道实现导致，不能宣称客户端已消除该 VPN 的全部慢速。没有切换订阅、节点或规则。

诊断下载与临时文件已清理，VPN 恢复测试前的关闭状态；设备覆盖安装正常候选包，保留原应用数据。临时诊断页面未进入源代码提交或发布制品。
