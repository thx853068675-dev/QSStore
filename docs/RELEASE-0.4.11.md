## 0.4.11 新增

### 刷新慢的根因：设备往返次数随应用数量线性增长

服务端不是瓶颈 —— `/api/v1/apps` 实测 55–70ms（服务器本机回环 1.7ms）。慢在客户端：
**每次刷新要做 `2 + 2N` 次设备往返**（N = 目录里的应用数）：

```
对账:      connected() 1 次 + 每个应用 isInstalled() N 次
版本核实:  connected() 1 次 + 每个应用 再 N 次
```

3 个应用就是 8 次；应用一多就十几秒。每次往返背后是一条经无线调试发到设备的
`bm dump` 命令。

改动：

- **新增批量查询操作码**（Rust 层 `bm dump -a`）：一次列出设备上全部包名，把
  「一个包一次往返」压成 1 次。对账现在只问一次设备，不再随应用数量增长。
  这条路径同时带走了「应用越多越慢」的问题。
- **`connected()` 先用已知链路状态短路**。`deviceLinked()` 一直在维护（每条成功的
  HDC 命令都会置位），但**从来没人调用**；于是 `connected()` 每次都白跑一次
  `bm get --udid` 往返。现在链路已知可用就直接返回。
- 批量列表**解析不出任何包名时返回「无法核实」**，而不是空集合 —— 否则一次解析
  失败会把全部安装记录误判成已卸载。

### 保留的保守语义

- 只有设备**明确回答**「没有这个包」才删记录；查询失败、设备没连、输出解析不出
  包名一律按「不确定」处理并保留。
- 新增测试锁定「对账只问设备一次，不随应用数量增长」这条不变量。
