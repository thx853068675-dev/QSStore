# 48 预览版 1：APP、ZIP 与多包上架

## 实现

- 本地文件支持 `.hap`、`.app`、`.zip`。ZIP 枚举有效 APP/HAP，用户选择后预览；点击安装才入队。APP 校验模块的包名、版本和模块名一致性，优先 entry 模块作为展示信息。
- ZIP 解压采用原生流式处理；限制 32 个安装包、2GiB 总展开大小与 200 倍压缩比。使用生成的临时路径，拒绝不安全路径、重复条目、加密、CRC 错误、截断与错误清单；取消时清理任务派生文件。
- APP 内所有 HAP 重签后一次 `bm install -p` 提交模块；保留现有内嵌工作模块重签。每个模块传输完成且设备摘要一致后才提交安装，失败清理设备暂存目录。
- 上架预处理异步检查 APP/ZIP；草稿持久化，重启恢复。确认允许多个经过检查的包，发布原子写入，并用后台任务补齐元数据。
- 服务端返回 `latest_assets`，保留 `latest_asset`；客户端按包身份匹配本地安装、管理更新与选中任务。多变体无法唯一匹配时，进入详情手动选择，避免自动选错。
- 服务端公布 `supports_multi_select`，客户端兼容旧服务端的单包模式；新服务端接受旧客户端的 `asset_name`，多包使用 `asset_names`。

## 验证

- 客户端 Node 244/244、服务端 96/96、C++ 核心 17/17、Rust 10/10、无签名检查 3/3。
- 正式包名干净构建 33/33；发布包递归检查无签名，没有内嵌 HAP。官方签名后的验证候选包通过 SDK 验签并覆盖安装到 HarmonyOS 6.1/API 24。
- 使用下载中的 HarmonyX 1.8.0 APP 实机验证预览名称、版本与模块；混合 ZIP 正确排除伪 HAP，在 APP 与 HAP 之间选择时刷新信息。原始文件未修改。
- 原生解压真实 HarmonyX HAP 的 SHA-256 与原包完全一致；实机发现的 deflate refill 边界错误已修复并加入大块随机内容测试。
- 用真实安装器 HAP 组装 APP，经 Rust APP 签名入口重签，各模块官方验签通过；拆出的签名 HAP 用设备 `bm install -p` 安装成功。外层 APP 容器不直接提交给设备安装器。
- 当前设备账号申请 AGC Profile 返回 `cert not exist`，没有为验证删除或新增开发者证书；未声称完成该账号下 APP 的应用内全流程安装。原有 Kazumi 暂停任务保留。
