# 发现页下拉识别：分析与验证

日期：2026-10-02。修复纳入 `0.4.49-preview.1 / 2026100202`。

## 测量范围

HarmonyOS 6.1、API 24 真机。服务端目录有 30 个应用、28 个不同包名；设备上命中安装器和轻启两个应用。安装器本身可直接由系统确认，因此完整下拉识别实际核对 27 个包名，只需通过无线链路查询其中 1 个已装应用的版本。测量时没有正在执行的安装任务。

分开测量三种入口，避免混用结果：

- 桌面 HTTP 请求：目录响应约 0.13～0.14 秒，仅作为网络基线。
- SDK HDC 直接 USB 查询：包名清单约 0.18～0.19 秒，仅作为设备命令基线。
- USB 转发到手机上安装器的内置 HDC 服务，再由该服务走手机的真实无线调试链路：用于同入口修复前后对照。最终又通过应用内下拉操作及分段日志验证实际识别。

## 原因

### 1. 每条命令固定多等 800 毫秒

内置 HDC 服务接受连接后，先等客户端发来 DevEco 格式的头，超时后才按标准 HDC 处理。但安装器的标准客户端必须先收到服务端 hello，才会发出自己的头。

双方因此一直互相等待，直到服务端的 800 毫秒协议探测超时。读取 UDID、包名清单、每个应用的版本，都各自重新建立命令通道，所以这段等待被反复支付。

修复：安装器内置服务明确使用标准 HDC 握手，立即发送 hello；独立服务的 IDE 自动识别路径保留。没有缩短设备授权、安装或证书校验的超时。

若有 K 个目标应用需要无线查询版本，正常扫描会执行 UDID、包名清单和 K 次详情查询；旧路径仅这项固定等待就约为 `0.8 × (2 + K)` 秒。此公式是代码路径推导，不是大量应用场景的真机测速结果。

### 2. 包名清单没有版本号

6.1 真机的 `bm dump -a` 只给包名。不能用它判断是否需要更新，仍需对清单中存在的目标应用读取 `bm dump -n`。

原有原生注释把“批量获取包名”写成“一次问完、不再随应用数增长”，并不准确，已修正。

修复后的调度先按包名去重，系统能实时确认的应用免走无线调试。系统权限不足时，仍读取真实设备信息；仅查询确实出现在设备清单中的目标包。

### 3. 失败查询重复读取完整清单

旧的逐包方法解析失败后会再查询一次完整包名清单。批量识别已经拿过清单，多个应用解析失败时会再次放大耗时。

修复：整轮识别共用一次清单；某个包详情异常时保留“存在、版本未知”，继续核对其他包。链路失败则停止后续版本查询，保留已知状态，避免继续串行超时。

### 4. 页面反馈与管理版本落后

旧页面等整轮结果返回后才更新按钮；管理页还会在系统查询无权限时继续显示历史安装版本。

真机发现：轻启实际版本为 `1.2.1-beta / 120101`，管理页仍显示历史 `1.1.0`。

修复：每项实时结果到达后更新对应卡片；未安装包不逐项重算整张管理列表。保存与具体构建绑定的设备版本名，管理页展示当前设备观察，安装历史保持原值。

## 结果

同一设备、同一转发入口，每项重复三次，表中为中位数：

| 查询 | 修复前 | 修复后 |
| --- | ---: | ---: |
| UDID | 944 ms | 101 ms |
| 包名清单 | 933 ms | 132 ms |
| 轻启版本详情 | 953 ms | 151 ms |

最终候选包在应用内连续三次下拉识别：

| 次数 | 核对包名 | 无线版本查询 | 整轮识别 |
| --- | ---: | ---: | ---: |
| 1 | 27 | 1 | 334 ms |
| 2 | 27 | 1 | 281 ms |
| 3 | 27 | 1 | 328 ms |

每次都真实执行版本查询，未使用一分钟缓存跳过查询。上述整轮识别从设备扫描开始计时，目录网络请求另计；不能把它当作所有用户、所有网络下整个下拉过程的保证。

其中第三次应用内命令耗时为：UDID 72 ms，包名清单 120 ms，版本详情 91 ms；命令排队为 0～1 ms。其余时间包括缓存读取、逐项界面反馈和结果落盘。

保留诊断日志：目录请求、系统调度、命令排队与执行、扫描总耗时、页面最终协调。只记录耗时与计数，目录日志不记录用户搜索词。

最终加入分段日志后的另一轮真机操作：目录读取 47 ms、系统状态整理 14 ms、无线识别 312 ms、最终协调 25 ms，从目录请求开始到状态协调完成约 0.40 秒。管理页同时实测显示 `1.2.1-beta`，没有继续沿用历史 `1.1.0`。这是已连接、目录已有 ETag 缓存的测量。

## 正确性与取舍

- 去掉本次最初尝试的“一分钟内跳过实时版本查询”。显示缓存仍供离线展示，主动下拉始终重新核对版本。
- 查不到或链路失败不等于未安装；只有可靠包名清单中的缺席才清理记录。
- 部分版本查询失败时，历史显示缓存不能把这一轮记为完整识别。
- 安装完成判定仍使用实时证据，不能由历史缓存完成暂停任务。
- 命令保持串行，避免查询越过正在提交的安装。等待安装的时间单独记为 queueMs。
- 测试过把两个 `bm dump` 合并为单条 shell：USB 基线约 0.55～0.65 秒，两个独立查询合计约 0.38 秒；没有采用未经证明更快的批量 shell 改造。
- 识别卡片移除。下拉等待这一轮真实设备识别与合并进来的补查完成后收回；图标下载、完整目录同步仍在后台。下拉读取已有服务端目录，不触发 GitHub 采集。
- 识别通过现有设备桥先自动尝试保存端口。若无线链路确实断开，弹出连接窗口；连接成功后继续同一批扫描，关闭窗口或离开页面会结束本轮等待，保留原有状态。清单解析失败或单个版本未知不误报为需要重新连接。

## 验证

442 项回归测试通过：客户端 294、服务端 106、C++ 17、无签名制品 3、Rust 签名 12、HDC 10。

新增用例覆盖：标准握手不等待 IDE 超时；新鲜显示缓存下仍发现外部更新与卸载；部分失败不重复扫描、不删除缓存；包名去重与跳过系统已确认包；单项结果立即更新按钮；不完整识别不被旧缓存标记成功；设备版本名跨进程保存且不串用构建；管理当前版本与历史记录分离。

执行全量 ArkTS/原生构建及递归无签名检查。真机候选包沿用设备已有签名材料，经官方 SDK 签名、verify-app 和覆盖安装验证，没有申请新证书。

## 实际边界

本次真机只有 1 个需要无线版本查询的商店应用；更多已装目标仍需执行更多设备查询。修复消除了每条命令固定 800 毫秒等待，没有宣称查询数量不再影响总时间。

端口变更、系统授权尚未完成、无线调试服务无响应和安装占用命令队列，仍可能带来额外等待。现有状态保留与重连行为继续生效；这些场景通过日志可与正常扫描区分。没有用并发安装、伪造完成进度或抹掉历史状态换取表面速度。

## 证书状态与授权等待

额外确认并修复：

1. 安装任务自动获取证书后，只更新沙箱材料，没有通知“我的”页面重新读取证书；页面可以一直显示旧的“待申请”。现在材料成功落盘后发布进程内版本通知，页面只读取本机配对材料，不增加 AGC 请求。
2. 申请或恢复证书成功后，没有唤醒等待账号/证书条件的旧任务；启动时登录恢复会触发这个唤醒，因此容易表现为重启后才继续。现在材料变化会唤醒 `WAITING_ACCOUNT`，已有活动任务保持去重。
3. 启动恢复与安装恢复过去可以重复请求同一份备份；现在同账号、团队、沙箱共享恢复任务，主动强制刷新等待普通恢复完成后再执行。失败会释放任务，允许同一进程重试。

“卡在 75%”不能单独定位具体故障。当前分阶段界面不再把授权里程碑当作精确总百分比。签名身份准备、恢复和每种 AGC 请求现在分别记录耗时（不记录令牌、私钥或用户 ID），下次能区分证书恢复、账号刷新、设备登记与授权签发。网络或 AGC 抖动仍可能造成等待，不能声称本次实机重现了该偶发故障。

补充回归覆盖：下拉等待已有识别及新增补查、连接失败后的原批次继续、取消释放等待、打开系统设置后保留等待；快照落盘期间到达的新包也等待核对完成。

最终候选包真机：无线调试关闭后，下拉自动重连失败显示连接窗口，刷新指示器保持转动。进入系统设置会保留本轮等待（此前真机发现这里会错误取消，已修复）；返回后连接窗口及原端口仍保留。

实机已跑通保存端口失效的场景：端口由 38019 变为 34747；进入设置后返回，刷新与连接窗口仍保留。输入新端口连接成功后，本轮扫描核对 27 个包名、查询 1 个版本，扫描 333 ms，协调 9 ms，随后才记录刷新完成。日志总等待含人工操作时间，不作为识别性能。
